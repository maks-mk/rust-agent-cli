# Аудит производительности Rust CLI Agent

Дата: 4 ноября 2026 года. Задание: `tz.md`. Исходный commit:
`735e2d6024dea4e9c58eda8a6a61c47d061cfc8c`. Пользовательские изменения `tz.md` сохранены.
Замеры и полный набор проверок выполнены до bump версии; оптимизации включены в
версию 0.1.8. Исходные логи сохраняют фактическую версию запуска 0.1.7.

## Карта потоков данных

1. `main::main` загружает конфигурацию → `inline::start` создаёт `App`.
2. `App::submit` переносит ввод в историю, UI и историю ввода, сохраняет сессию.
3. `App::start_run` создаёт отдельную Tokio-задачу с копией истории и дешёвыми
   клонами `reqwest::Client`/`Arc`. UI сохраняет свою историю для отмены и сохранения.
4. `agent::run_turn` загружает MCP-конфигурацию, собирает схемы инструментов и
   системный промпт. В цикле оценивает контекст, при необходимости сжимает историю,
   отправляет Chat Completions или Responses запрос.
5. `completion_with_retries` управляет повторами; `stream_completion` сериализует
   запрос, получает HTTP-чанки, собирает SSE-строки, разбирает JSON, накапливает
   текст, reasoning, аргументы инструментов и usage. Через `AgentEvent` передаёт
   принадлежащие событиям строки в UI.
6. `Completion` преобразуется в сообщение истории. `ToolBatch` резервирует ответы
   на все вызовы, выполняет группы чтения/shell до четырёх параллельно; остальные
   инструменты последовательно. Изменения истории отправляются патчами; при отмене
   остаются корректные пары tool call/result.
7. `App::on_agent` обновляет UI/историю; `SessionWriter` пишет снимки в отдельном
   потоке с одной заменяемой ожидающей записью. `HistoryState` кэширует строки UI;
   `inline::run` объединяет события, ограничивает частоту кадров примерно 29 FPS.

Основные runtime-зависимости: Tokio, reqwest, serde/serde_json, futures-util,
ratatui/crossterm, image, similar, command-group, tempfile, chrono, anyhow.
HTTP-клиенты приложения и HTTP MCP уже переиспользуются. RAG отсутствует и не добавлялся.

## A. Обнаруженные проблемы

| Файл / функция | Проверенная причина затрат | Частота / масштаб | Серьёзность | Выполненное исправление |
|---|---|---|---|---|
| `src/agent.rs`, `run_turn`, `completion_request` | Глубокий clone истории в `messages`, затем повторное копирование в JSON-тело; копируются схемы tools | Каждый шаг, включая цепочки инструментов; пропорционально всей истории | Высокая | Ссылки на историю/схемы, типизированный сериализуемый запрос |
| `src/agent.rs`, `estimate_tokens` | Полная сериализация в временную строку только для получения её длины; Responses дополнительно клонирует raw output перед удалением | Несколько раз на шаг и при обновлении UI; пропорционально истории | Высокая | Счётчик байтов и сериализация отфильтрованной карты по ссылке |
| `src/agent.rs`, `stream_completion` | `from_utf8_lossy(...).trim().to_string()` создаёт строку на завершённую SSE-строку перед JSON-парсером | Тысячи коротких событий или одна большая строка | Средняя | Разбор из существующего буфера без промежуточной owned-строки |
| `src/agent.rs`, `stream_completion`, `Completion::assistant_message` | Копирование полного массива `response.output`, затем повторное копирование текста и raw output в историю | На каждый Responses ответ; до лимита ответа | Высокая для больших ответов | Перенос через `take`, освобождение временного тела запроса до чтения ответа |
| `src/agent.rs`, `responses_input` | Копирование сохранённых Responses output items при продолжении, даже когда их формат уже подходит API | Каждый следующий запрос Responses | Средняя/высокая | `Cow<Value>` для заимствования готовых output items |

`Vec::new` и `String::new` сами не выделяют heap. `push_str` выделяет память только
при недостаточной capacity. `clone` строк и JSON-массивов копирует данные, а clone
HTTP-клиента/`Arc` разделяет существующее состояние. `format!` для коротких сообщений
об ошибке, путей и одноразового системного промпта не объявлялся проблемой сам по себе.

## B. Выполненные изменения

- `src/agent.rs`: рабочий список запроса содержит ссылки на системное сообщение и
  историю вместо глубоких копий. Размер контейнера резервируется заранее. Сигнатура
  публичного `run_turn` и владение историей в UI не изменены.
- `src/agent/request.rs`: приватные типизированные тела Chat/Responses сериализуются
  непосредственно через `reqwest::RequestBuilder::json`. Chat использует ссылки на
  сообщения и схемы. Необязательные поля по-прежнему отсутствуют при `None`.
  Преобразованный Responses input освобождается сразу после сериализации запроса.
- `src/agent/json_size.rs`: writer считает байты той же serde_json-сериализации без
  результирующей строки. Представление `VisibleMessage` пропускает raw Responses
  output без предварительного копирования. Unicode, JSON escaping и округление
  оценки токенов сохранены; обработка изображений оставляет прежнюю оценку vision.
- `src/agent.rs`, SSE: парсер использует `Cow<str>` от `from_utf8_lossy` непосредственно
  из переиспользуемого буфера. Буфер очищается после разбора. Для корректного UTF-8
  отдельная строка перед парсером не выделяется; прежняя lossy-обработка сохранена.
- `src/agent.rs`, Responses/история: `Value::take`, `Option::take` и `mem::take`
  переносят output items, текст и reasoning. Tool arguments остаются доступными
  исполнителю. Результат file tool также переносится в `Value::String`.
- `responses_input` использует `Cow<Value>`: уже сохранённые output items
  сериализуются по ссылке, а сообщения, требующие преобразования формата, остаются
  owned. Убраны промежуточная копия строкового tool output и копирование
  преобразованного content; JSON-значения tool output по-прежнему сериализуются в строку.
- `src/agent/performance_tests.rs`, `src/agent_tests.rs`, `src/agent/tests.rs`:
  регрессии сериализации, оценки контекста, переноса ответа и SSE; существующие тесты
  адаптированы к приватным функциям без ослабления проверок.
- `Cargo.toml`/`Cargo.lock`, `src/agent/performance.rs`: Criterion, stats_alloc и DHAT
  только в dev-dependencies. Аллокаторы включаются только под `cfg(test)` с отдельным
  feature; обычная Release-сборка их не содержит. `cargo tree --edges normal`
  подтверждает отсутствие этих трёх библиотек среди runtime-зависимостей.
- `scripts/measure-performance.ps1`, `scripts/check-performance.ps1`: воспроизводимые
  измерения и проверки с сохранением логов. `docs/performance/` содержит исходные
  результаты двух состояний проекта.

Новые runtime-зависимости, unsafe-код, кэши с неограниченным временем жизни и изменения
публичных интерфейсов не добавлялись. JSON-поля API, механизм инструментов, лимиты,
повторы, события usage и отмена сохранены.

## C. Результаты измерений

Среда: Windows x86_64 MSVC, Rust 1.99.1, Cargo 1.99.1. Release: opt-level=3,
thin LTO, codegen-units=1. Во время замеров нет обращений к внешней модели.

Воспроизведение в PowerShell из корня проекта:

```powershell
./scripts/measure-performance.ps1 -Label optimized
```

Скрипт сохраняет исходные логи, Criterion estimates с доверительными интервалами,
версию компилятора, commit и показатели рабочего набора процесса в
`docs/performance/<label>/`. Для baseline надо запускать его на исходном production
коде с добавленным стендом; повтор на оптимизированном коде не восстанавливает baseline.

Можно запускать профили отдельно:

```powershell
cargo test --release --lib agent::performance::timing -- --exact --ignored --nocapture --test-threads=1
cargo test --release --lib --features profile-allocations agent::performance::profile -- --exact --ignored --nocapture --test-threads=1
cargo test --release --lib --features profile-heap agent::performance::profile -- --exact --ignored --nocapture --test-threads=1
```

Стенд `src/agent/performance.rs` вызывает настоящий `run_turn` и настоящий HTTP/SSE
клиент. Локальный сервер отдаёт фиксированные ответы; consumer забирает события.
Клиент, runtime, временный workspace и входные fixtures создаются до измерения.
Сжатие контекста в стенде отключено (`context_tokens=0`), чтобы изолировать заданную
нагрузку и не включать дополнительный запрос к summarizer; его корректность проверяют
существующие функциональные тесты.
Создание локального listener, чтение запроса mock-сервером, клонирование начальной
истории, выполнение file tools и освобождение результата включены. Каждый профиль
памяти предваряется прогревочным запросом. Это измерение движка с mock API, без
отрисовки терминала, фонового сохранения сессий и внешних MCP-серверов.

| Сценарий | Нагрузка |
|---|---|
| `plain` | Один пользовательский запрос, текстовый ответ без вызовов инструментов |
| `history_30` | 30 сообщений, каждое содержит 2048 повторов строки с Unicode |
| `tools_3` | Три последовательных `read_file`, затем итоговый ответ; файл 2000 строк |
| `stream_2048` | 2048 SSE-событий с `я🙂`; mock пишет фрагменты по 17 байт с yield |
| `large_json` | Responses completed с 12000 повторами `Большой ответ 🙂\n` |
| `requests_100` | 100 последовательных `plain` с одним клиентом/MCP/runtime и освобождением каждого результата |

TCP может объединять записи mock-сервера. Разбиение UTF-8 на всех границах проверяют
отдельные функциональные тесты; число TCP read не предполагается постоянным.

Criterion работает с системным аллокатором без профилирования, 20 выборок,
1 секунда прогрева и целевые 3 секунды измерения на сценарий. Накладные расходы
локального HTTP и планировщика входят во время. `stats_alloc` считает allocation,
reallocation и запрошенные байты (при росте realloc учитывает приращение).
DHAT отдельно измеряет пиковые живые байты и оставшиеся живые байты выделений,
сделанных внутри области профилирования; заранее созданные fixtures туда не входят.
Время под DHAT не используется для сравнения скорости.

Суммарные выделения не равны потреблению памяти. Рабочий набор Windows измеряется
на уровне всего тестового процесса; он включает код, runtime, fixtures и тестовый
стенд. PowerShell каждые 20 мс читает OS peak working set и текущие private bytes.
Это не метрика одного запроса; пик private bytes является выборочным. Изменения
рабочего набора зависят также от системного аллокатора и планировщика.

### Память после завершения

Во всех шести сценариях до и после оптимизации `stats_alloc` показал чистый прирост
занятых байтов **0**, DHAT — **40** живых байт из выделений текущей области профиля.
После 100 запросов эти показатели не выросли относительно одного запроса. DHAT не
включает объекты, созданные до начала области, поэтому его остаток не равен чистому
приросту всей кучи. Состояние harness/client остаётся жить между запросами.

`dhat.total_bytes` сохранён в исходных логах отдельно. Он учитывает полный размер
нового блока при realloc, тогда как `stats_alloc.bytes_allocated` добавляет только
положительное приращение. Например, рост 128 → 256 байт даёт суммарно 384 байта по
первому правилу и 256 по второму. Эти суммы не смешиваются и не выдаются за пик heap.

### Контрольная пара времени

После сборок последовательно запущены сохранённые baseline и optimized тестовые
EXE без профилирующего аллокатора, с теми же шестью сценариями и настройками Criterion.
Повтор понадобился из-за малого эффекта streaming и вариативности обычного HTTP
запроса. Исходные данные: `baseline-confirmation/` и `optimized-confirmation/`.

| Сценарий | До, мс | После, мс | Изменение |
|---|---:|---:|---:|
| `plain` | 1,314 | 1,251 | −4,8% |
| `history_30` | 15,531 | 11,007 | −29,1% |
| `tools_3` | 7,299 | 6,511 | −10,8% |
| `stream_2048` | 150,833 | 149,585 | −0,8% |
| `large_json` | 6,311 | 5,672 | −10,1% |
| `requests_100` | 137,454 | 101,389 | −26,2% |

Для обычного запроса и streaming Criterion в этой паре **не обнаружил значимого
изменения времени**. Ускорение длинной истории, трёх tools и большого JSON
подтвердилось. В серии 100 запросов baseline имеет широкий доверительный интервал;
точный процент ускорения этой серии не следует считать стабильной константой.
Оба прогона полностью сохранены, результаты первого не заменены более выгодными.
В `baseline-confirmation/timing.txt` строки `change` сравнивают старый EXE с
предыдущим optimized запуском; таблица выше явно сравнивает baseline с optimized
внутри контрольной пары.

Дополнительно пройден `cargo clippy --all-targets --all-features -- -D warnings`.
Собранный `target/release/rust-agent.exe --help` успешно запускается. Размер EXE:
5 933 056 → 5 946 880 байт (+13 824 байта, +0,23%); профилировщики отсутствуют в
runtime-графе зависимостей. Уменьшение размера исполняемого файла не заявляется.
Два профилировочных теста в каждом бинарнике помечены ignored и запускались отдельно
для всех шести сценариев. Они проверяют итоговый текст и число tool results.
Из существующих ignored-тестов не запускались `context7_live` (реальный внешний
Context7 endpoint) и `frame_cost_is_independent_of_completed_history` (ручной
benchmark renderer). Внешний сервис исключён из локальных измерений; UI не менялся
и не включён в сравнение производительности.

Новые регрессии проверяют:

- эквивалентность оценки размера JSON для Unicode, escaping, чисел, изображений и
  исключения raw Responses items;
- точные поля Chat-запроса с включёнными/отсутствующими tools и reasoning;
- сохранение raw Responses items, encrypted reasoning, дополнительных полей и
  сериализации нестрокового результата инструмента;
- сохранение текста, reasoning и tool calls при переносе ответа в историю;
- SSE с Unicode, CRLF, игнорируемыми/некорректными строками и разными границами чанков.

Также прошли прежние тесты retry/EOF/ошибок, лимитов ответа, usage, сжатия контекста,
параллельных инструментов, отмены, файлов, изображений, MCP, сохранения сессий и UI.
Во время разработки исправлены замечания строгого Clippy к новым тестовым
предусловиям и ставшим ненужными `Vec` фиксированной длины. Логи в `baseline/` и
`optimized/` отражают завершённые проверки соответствующего этапа.

## E. Оставшиеся проблемы и границы аудита

- `App::start_run`, `autosave`, `SessionStore::queue_save`: копии истории для UI,
  активной задачи и фонового снимка действительно существуют. Замена на общее
  изменяемое хранилище затрагивает отмену, восстановление и согласованность записи.
  Следующий отдельный этап: профиль событий autosave и batching неизменённых
  снимков с тестами отмены/падения writer. Сейчас архитектура сохранена.
- Сжатие истории ограничивается порогом контекста; при `context_tokens=0` пользователь
  явно отключает его. UI, история ввода и сессионная история могут расти. Автоматическое
  удаление изменило бы функциональность. Серия 100 запросов проверяет временные
  объекты, а не доказывает отсутствие роста в бесконечно сохраняемом диалоге.
- `background::JOBS` удерживает записи завершённых заданий ради `list/status`, а логи
  фоновых процессов могут расти на диске. Нужна отдельно согласованная политика
  очистки/лимитов; это не цикл `Arc` и не исправляется молчаливым удалением истории.
- UI кэширует все отформатированные строки; при большом растущем ответе повторно
  форматирует активную запись. Нужен отдельный benchmark терминального renderer
  перед изменением кэша. Замеры движка не дают основания заявлять ускорение UI.
- MCP собирает схемы на границе turn, копирует некоторые параметры/описания.
  Изменение регистрации, переподключения и session retry без отдельного MCP-профиля
  не выполнялось. Клиенты, блокировки и ограниченные буферы уже используются.
- Очередь `AgentEvent` неограниченная; wire-limit ответа 32 MiB ограничивает объём
  одного ответа, но не накладные расходы множества очень мелких событий. Backpressure
  требует отдельного решения с тестами отмены и скорости UI.
- Сохранённые Responses output items нужны для stateless continuation, в том числе
  reasoning. Их дублирование с видимым текстом в постоянной истории сохранено ради
  совместимости формата и функциональности.

Проверенные ограничения: SSE line 1 MiB, ответ модели 32 MiB, 128 tool calls,
HTTP error body 16 KiB, ограниченные head/tail shell output, ограниченные размеры
изображений и MCP сообщений. Нет оснований объявлять отсутствие всех возможных
утечек: проверены конкретные сценарии и время жизни объектов в исследованных потоках.

## F. Заключение

Во всех шести сценариях уменьшились количество аллокаций, суммарные выделения и
пик живых выделений. Количество аллокаций снизилось на **9,1–53,8%**, суммарные
выделения stats_alloc — на **4,1–57,2%**, пиковый heap — на **24,1–46,4%**.

Наиболее существенные результаты:

- История из 30 сообщений: 1130 → 532 аллокации (**−52,9%**), realloc 833 → 34
  (**−95,9%**), выделения 13,16 → 5,82 МБ (**−55,8%**), пик 8,82 → 5,79 МБ
  (**−34,3%**). Контрольное время 15,53 → 11,01 мс (**−29,1%**).
- Большой JSON: выделения 5,17 → 2,21 МБ (**−57,2%**), пик 3,00 → 1,61 МБ
  (**−46,4%**); контрольное время 6,31 → 5,67 мс (**−10,1%**).
- Три последовательных инструмента: аллокации **−53,8%**, выделения **−42,5%**,
  контрольное время **−10,8%**.
- Streaming: аллокации **−9,1%**, пик heap **−24,1%**. Достоверное изменение времени
  не установлено; оптимизация сохранена из-за измеримого уменьшения затрат памяти.
- 100 последовательных запросов: аллокации 63 502 → 38 502; чистый прирост занятых
  байтов после серии остаётся нулевым. Это результат ограниченного сценария,
  а не утверждение об отсутствии любых утечек или роста пользовательской истории.

МБ здесь десятичные (1 МБ = 1 000 000 байт); точные байты приведены в таблицах.
Подтверждён эффект устранения временных копий истории/JSON, подсчёта размера без
строкового буфера и переноса готового ответа. Измерен пакет изменений целиком;
вклад каждой отдельной правки независимо не измерялся. Ускорение зависит от
нагрузки: для обычного короткого запроса оно не подтверждено контрольной парой.

Обычная архитектура, публичные API, форматы сообщений и поведение инструментов
сохранены; обязательные проверки и функциональные сценарии пройдены. Дальнейшее
внимание стоит уделить snapshots/autosave, росту UI-истории, мелким JSON/SSE-событиям
и MCP. Их изменение требует собственных измерений, а не переноса процентов из
данного стенда на всё приложение.
